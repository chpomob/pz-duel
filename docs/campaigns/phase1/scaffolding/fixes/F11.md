## Constats à corriger

### A5 [minor] service/api.py:215 — The single-user-machine assumption behind the local API and argv secrets is undocumented

**Preuve de la revue** : _refused only stops browsers: any local process that sends Host: 127.0.0.1:<port> with no Origin gets /api/state, whose config holds both player passwords (host_password and password), and can POST start or cancel. No token is required. servers.py:171 also puts the admin password on the server's argv, visible in ps to other local users, while the README only warns about the client password. Assumption: the host is a single-user desktop, in which case the exposure is small. On a shared machine, any local account could read the passwords and drive the duel. Fix: state the assumption in the README and limites-connues.md, or add a per-run token issued in the URL printed at startup, and strip host_password from /api/state outside the lobby.

**Correction attendue** : Documente l'hypothèse « machine mono-utilisateur » dans `README.md` et `docs/campaigns/phase1/limites-connues.md`, et retire `host_password` de `/api/state` hors lobby. Test : en match, la réponse de `/api/state` ne contient plus ce champ ; en lobby, si.

### A6 [nit] service/engine.py:1411 — open_game has no phase guard and can launch clients at servers that are down

**Preuve de la revue** : _open_game_real checks only that config holds a password, and config survives over, error and cancel (_cancel_state does not clear it). Pressing the action in those phases, or during preflight, starts an untracked client aimed at a stopped server. Each call runs outside the lock and blocks its HTTP thread for 2 s, so repeated calls start several clients. Fix: accept only lobby-related phases and refuse a second launch while one is alive.

**Correction attendue** : `open_game` n'accepte que les phases de lobby et refuse un second lancement tant qu'un client est vivant ; hors de ces phases, refus explicite. Test : appel en phase `match`, en `error` et en `preflight` → refus, aucun processus lancé ; deux appels rapprochés → un seul lancement.

### A7 [nit] service/engine.py:548 — Comments and the spec still state H3 after the README recorded it as contradicted

**Preuve de la revue** : README 'Premier contact' says H3 is contradicted: with PauseEmpty=false an empty server ticks and beats every 10 s. engine.py:548 and engine.py:791 still give 'un serveur vide ne tique pas' as the reason for their behaviour, spec.md:127 still asserts it, and tests/test_match.py:1190 models that behaviour. In _track_age the stated reason is now false: the first beat after a restart no longer waits for the player to reconnect. Behaviour looks acceptable, but the next reader will reason from a disproved premise. Fix: update the comments and spec, and make the test double match the observed behaviour.

**Correction attendue** : Corrige les commentaires et la spec qui affirment encore « un serveur vide ne tique pas » (contredit par `PauseEmpty=false`), et aligne le double de test sur le comportement observé. Test : le double modélise un serveur vide qui tique et bat toutes les 10 s.
