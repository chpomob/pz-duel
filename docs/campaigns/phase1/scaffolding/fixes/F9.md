## Constats à corriger

### A1 [blocker] mods/duelcore/42.21/media/lua/server/DuelCore.lua:437 — damage_taken cannot fire in a duel, so the default preset can never leave the lobby in real mode

**Preuve de la revue** : Source: build 42.21.0 projectzomboid.jar, disassembled with javap on 2026-11-06. The string OnWeaponHitCharacter is triggered in exactly one place: zombie/characters/IsoGameCharacter.Hit(HandWeapon, IsoGameCharacter, float, boolean, float, boolean). The only callers found are WeaponHit.process (used by the PlayerHitZombie, PlayerHitPlayer, PlayerHitCharacter and PlayerHitAnimal packets), CombatManager.attackCollisionCheck (called only from SwipeStatePlayer) and IsoZombie.Hit. A zombie hitting a player takes another path: ZombieHitPlayerPacket.process -> Bite.process -> BodyDamage.AddRandomDamageFromZombie, and Bite contains no call to Hit (AttackState and FakeDeadAttackState also call AddRandomDamageFromZombie directly). So the hook fires only for a weapon hit by a player. onWeaponHitCharacter discards every non-player target (DuelCore.lua:438), and MaxPlayers=1 (runtime.json) with separate worlds leaves no second player to strike the first. hook_seen(OnWeaponHitCharacter) is therefore never emitted. Consequence in code: effects.json makes this hook the proof for damage_taken; ContractWindow withdraws the atom at the deadline; _close_window (engine.py:1074) revalidates with active_atoms and refuses the table. duel_rapide, the default preset (engine.py:1446), and pression both list damage_taken, so each ends in error after hook_window_s. Only demo and hardcore can reach the countdown. README 'Procédure de verdict en jeu' step 2 ('Faites-vous frapper par un zombie') cannot succeed, so AC19 cannot be closed by the documented procedure. This turns the earlier A4 concern (silent loss) into a certain refusal. The 1044 passing tests do not see it, because tests/test_lua_attribution.py:282 fires the hook by hand with a player target and tests/doubles/fake_mod.py:106 emits hook_seen itself. Not run with a real player: the conclusion is from bytecode only, and one zombie hit in a real session would confirm it. Fix: detect damage from a signal on the zombie path, such as a server-side health or BodyDamage delta in step(), or OnPlayerGetDamage (triggered in BodyDamage.Update and in Hit, but whether it runs on the server is unverified), and make that signal the hook_proof. Until then, drop damage_taken from the default preset.

**Correction attendue** : Prouve `damage_taken` par un signal du chemin zombie, pas par un coup d'arme : enregistre `OnBeingHitByZombie` (et `OnPlayerGetDamage` en complément), émets l'événement de dégâts avec les points de vie et l'attaquant quand il est connu, et n'émets `hook_seen` qu'à la première réception réelle. Corrige `effects.json`, le contrat et la procédure du README (on se fait mordre, pas frapper). Deuxième exigence, aussi importante : un atome dont la preuve n'arrive pas est retiré sans refuser toute la table — un preset reste jouable avec les atomes survivants, et seule une table sans aucun atome est refusée. `duel_rapide` (preset par défaut) doit atteindre le décompte même si `damage_taken` n'est pas prouvé. Tests : morsure simulée dans le double Lua → événement + hook_seen ; contrat où `damage_taken` ne prouve jamais → atome retiré, lancement poursuivi, effet dépendant désactivé ; preset par défaut lançable.

### A2 [minor] service/engine.py:1005 — A one-shot spawn probe turns a transient refusal into a torn-down launch and a solo_ipc fallback

**Preuve de la revue** : _send_probes sends one probe per side at first connection, and _take_probe_result marks any status other than applied as KO. _failed_probes then stops both servers and publishes fallback(KO, ...) = solo_ipc, the branch meaning server spawning does not work. The mod also answers refused (no_player, asleep, in_vehicle) and failed/no_square when PLACE_ATTEMPTS finds no free square, for example if chunks 30-60 tiles out are not loaded yet just after connecting. None of these says addZombiesInOutfit is broken. This matches the spec ('ko si elle revient autrement', spec.md:480-482; AC57), so the weakness is in the design as well as the code. Assumption: such states can occur at first connection; the README only records probe_spawn ending refused with no player. A real connection would confirm how often. Fix: retry within probe_timeout_s on refused and no_square, and keep KO for a persistent failure or a definite spawned=0.

**Correction attendue** : La sonde de spawn ne doit plus transformer un refus transitoire en échec définitif : sur `refused` et `no_square`, réessaie dans la fenêtre `probe_timeout_s` (avec un intervalle borné), et ne conclus KO que sur un échec persistant ou un `spawned=0` définitif. Test avec un double qui refuse deux fois puis applique : le lancement doit continuer.
