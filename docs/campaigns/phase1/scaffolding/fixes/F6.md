# F6 — Frontière HTTP infaillible et double Lua complet

commit: fix(phase1): F6 — Frontière HTTP infaillible et double Lua complet

## Contexte

Deuxième vérification des 18 constats : 16 RESOLVED, 1 PARTIAL réel (A6), 1 nouveau mineur
(le double `mini_lua`). Le PARTIAL A8 était un artefact de périmètre de lecture — vérifié à la
main : `service/servers.py:181` tire le mot de passe joueur par `secrets.token_hex(...)`,
générateur cryptographique, sortie hexadécimale. **A8 est donc fermé : n'y touche pas.**

## Constats à corriger

### A6 [major] — la classe « entrée qui fait lever la réponse HTTP » reste ouverte
`service/engine.py:1483-1491` et `service/api.py:111-113` ferment `DayLength` inconnu et corps
non objet. Mais en mode réel, `{"action":"start","preset":"\ud800"}` atteint
`service/engine.py:1316`, qui reprend le surrogate isolé dans `ActionRefused` ;
`service/api.py:49` lève ensuite `UnicodeEncodeError` sans réponse JSON.

**Correction attendue** : fermer la classe, pas le cas. Deux verrous indépendants :
1. Validation à la frontière : tout identifiant reçu (`action`, `preset`, `mode`, `side`, et tout
   champ de type identifiant ajouté plus tard) est refusé en 400 s'il n'est pas un identifiant
   ASCII sûr (lettres, chiffres, `_`, `-`, longueur bornée). Le refus est un message fixe, qui ne
   reprend jamais la valeur reçue.
2. Encodage infaillible : `service/api.py:_json` ne peut plus lever, quelle que soit la chaîne
   reçue (échappement des surrogates ou remplacement), avec un test unitaire direct sur `_json`.

Tests : requête HTTP réelle `start` avec `preset` = surrogate isolé → 400 JSON, pas de 500 ni de
connexion coupée ; test unitaire de `_json` avec un surrogate dans le message et dans une clé.

### NEW [minor] — le double `mini_lua` ne couvre pas l'API que le mod appelle
`tests/doubles/mini_lua.py:433-447` fournit `table.concat` mais pas `table.remove`, pourtant
appelée par `DuelCore.lua:816` ; `math.floor` délègue directement à Python, dont le comportement
sur l'infini diffère de Lua.

**Correction attendue** : le double couvre toute la surface que le mod utilise réellement.
1. Implémente les fonctions manquantes, dont `table.remove`, avec la sémantique Lua (décalage,
   retour de la valeur retirée, `#` recalculé).
2. Aligne `math.floor`/`math.ceil` sur Lua (conversion en entier, cas infini/NaN traités comme
   Lua les traite, pas comme Python).
3. Ajoute un test qui balaie `DuelCore.lua` à la recherche de `table.X`, `math.X`, `string.X`,
   `os.X` et échoue si le double n'implémente pas l'une des fonctions trouvées. C'est ce test qui
   empêche la classe de se rouvrir au prochain ajout dans le mod.
4. Documente dans le docstring du double les écarts assumés qui restent (objets Java simulés,
   `#` en caractères) et pourquoi ils ne peuvent pas fausser les preuves actuelles.
