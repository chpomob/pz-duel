# P9F30 — Les tests posent l'état par l'entrée du produit, pas en écrivant dans l'état

commit: fix(phase3): P9F30 — tests de lobby par la sonde du serveur, plus d'écriture directe dans l'état

## Contexte

CI rouge sur `733dd79` (P9F29), un seul job : `pytest (3.14)`.

    FAILED tests/test_platform_windows.py::test_missing_client_reveals_no_password[windows]
    assert 'ProjectZomboid64.exe absent' in "impossible d'ouvrir le jeu : l'adversaire n'est pas
    encore connecté…"

Le test veut vérifier qu'un client manquant est signalé sans révéler de mot de passe. Il a échoué
parce que `open_game` a refusé pour une autre raison : l'invité n'était pas connecté.

Le test fabrique cet invité à la main :

    with engine.lock:
        engine.state.players["B"] = "invite"

mais le moteur **rafraîchit `players` depuis la sonde `players` des serveurs**, dans son propre fil
(`service/engine.py:1706`, puis `state.players = players` à la publication). Sur une machine lente,
ce rafraîchissement passe entre l'écriture du test et l'appel à `open_game`, et efface l'invité. En
local, le test gagne la course 20 fois sur 20 ; sur le runner 3.14, il l'a perdue.

Cinq endroits écrivent ainsi dans l'état (`tests/test_modes.py` quatre fois, `test_platform_windows.py`
une fois). Ce sont des tests qui simulent une **entrée** en écrivant une **sortie** : ils prouvent que
le code lit `state.players`, pas que le produit détecte un joueur.

Sixième occurrence de la famille des tests non déterministes (après P9F21, P9F24, P9F27, P9F28, P9F29),
et la première où la cause n'est pas le temps mais **le point d'injection**.

## Ce que l'étape doit faire

### 1. Poser l'invité par la sonde, comme le vrai serveur

Le double de serveur doit pouvoir annoncer des joueurs : `players -> "Players connected (2): invite"`.
Les cinq tests concernés s'en servent, attendent que l'état reflète la connexion — avec
`wait_until(..., what=…)` de `tests/doubles/waiting.py`, budget `PZDUEL_TEST_WAIT_S` — puis appellent
l'action.

Si un test a besoin d'un état que la sonde ne peut pas produire (par exemple un joueur qui disparaît),
il le dit : soit le double gagne la capacité, soit le test s'appuie sur l'API du produit qui provoque
cet état. Écrire dans `engine.state` n'est plus une option.

### 2. Une garde qui empêche le retour

`tests/test_ci_workflows.py` (ou le fichier de gardes du dépôt) parcourt `tests/` et échoue si un test
écrit directement dans l'état du moteur — motifs `state.players[`, `state.phase =`, moteur ou état
exposé — en nommant fichier et ligne. Un test qui a réellement besoin de forcer un état doit passer par
un double, et la garde ne doit pas gêner les doubles.

### 3. La preuve

- Les cinq tests concernés passent **20 fois de suite**.
- La suite complète passe, et la CI verte sur ce commit.
- Mutation vérifiée : remettre l'écriture directe dans un des tests doit faire échouer la garde.

## Règles

- Fichiers autorisés : `tests/test_modes.py`, `tests/test_platform_windows.py`, `tests/doubles/`,
  `tests/test_ci_workflows.py`, `docs/campaigns/phase3/limites-connues.md`.
- Aucun changement produit : le moteur garde son rafraîchissement, c'est le test qui s'aligne sur lui.
- Un seul commit, sujet exactement :
  `fix(phase3): P9F30 — tests de lobby par la sonde du serveur, plus d'écriture directe dans l'état`.

## Definition of done

- Plus aucune écriture directe dans l'état du moteur depuis `tests/`, et une garde le vérifie.
- Les cinq tests passent 20 fois de suite ; suite verte ; CI verte sur le commit.
- Réponse finale en français : ce que la sonde annonce désormais, comment les cinq tests attendent la
  connexion, et ce qui reste non couvert parce qu'aucune entrée ne peut le produire.
