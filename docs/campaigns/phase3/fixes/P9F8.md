# P9F8 — Des pops dispersés, et des zombies qui savent où on est

commit: feat(phase3): P9F8 — pops dispersés et ciblage à l'apparition, réglables sans retoucher le mod

## Contexte, retour de la première partie jouée

Deux retours du propriétaire après une partie réelle :

> « les z qui pop sont trop groupes, et ils savent pas ou on est, ca serait bien qu ils nous ciblent
> en apparaissant »

Diagnostic dans le code livré :
- `spawnAt(square, count, …)` crée **n zombies sur une seule case** (`addZombiesInOutfit(x, y, 0, count, …)`,
  `DuelCore.lua:678`) : pour un pop de 2, deux zombies superposés, qu'on voit apparaître d'un bloc.
- Rien n'oriente les zombies vers le joueur : ils naissent « au repos » et vaquent, donc l'effet punitif
  se perd — on peut les contourner sans les combattre.

L'API du jeu permet de faire mieux, vérifié par `javap` sur `zombie.characters.IsoZombie` :
`setTarget(IsoMovingObject)`, `addAggro(IsoMovingObject, float)`, `spotted(IsoMovingObject, boolean)`,
`clearAggroList()`.

## Ce que l'étape doit faire

### 1. Un pop dispersé, pas un tas

Dans le mod, chaque zombie du lot naît sur **sa propre case** : on tire autant de cases libres que
demandé, à une distance du joueur comprise dans la bande (`distance`), et **espacées entre elles d'au
moins `spacing` cases** (réglage décrit au point 3, défaut **4**). Si le mod ne trouve pas assez de
cases espacées après ses tentatives, il en accepte moins — et rend le nombre réellement créé, comme
aujourd'hui : `spawned` reste la vérité, jamais le nombre demandé.

Le refus `too_close` et le plancher `MIN_DISTANCE` restent tels quels.

### 2. Cibler le joueur en apparaissant

Après création, chaque zombie créé est **orienté vers le joueur** avant de rendre la main :
`setTarget(player)`, puis `addAggro(player, <poids>)`, puis `spotted(player, true)`, chaque appel
sous `pcall` : si une de ces fonctions n'existe pas sur une version du jeu, le spawn reste valide et le
résultat le dit (`targeted: false` dans le `cmd_result`), il ne casse pas.

Le résultat du `cmd_result` porte désormais `spawned`, `targeted` (nombre réellement ciblé) et
`spread` (nombre ayant obtenu une case espacée).

### 3. Les deux réglages voyagent dans la commande, pas dans le mod

`spacing` (cases, entier ≥ 0) et `aggro` (0 à 1, flottant ; `0` = aucun ciblage) sont **des champs de
la commande**, remplis par l'arbitre depuis le preset. Le mod les lit avec des valeurs de repli sûres
(`spacing` absent → 0 = comportement d'aujourd'hui, `aggro` absent → 0). Ainsi on règle le ressenti en
éditant un preset, sans réinstaller le mod ni faire retélécharger le `.bat` à l'invité.

Le preset `duel_rapide` reçoit `spacing: 4` et `aggro: 0.6` ; les trois autres presets sont mis à
`spacing: 4` et `aggro: 0.6` aussi, sauf `demo` qui garde `aggro: 0` (mode simulé, sans intérêt).

Validation côté arbitre, comme les autres réglages : `spacing` entier entre 0 et 20, `aggro` nombre
fini entre 0 et 1, refus du reste avec un message qui nomme la clé et la valeur.

### 4. Ce que le journal doit permettre de vérifier

`rule_fired` puis `cmd_result` doivent suffire à répondre, sans relire le code : combien de zombies ont
été créés, combien ont eu une case espacée, combien ont été ciblés. Si un lot rend `spawned: 2` mais
`spread: 1`, on doit le voir dans le journal.
