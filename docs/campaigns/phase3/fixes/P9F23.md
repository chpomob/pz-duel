# P9F23 — Les sorties de Node se lisent en UTF-8 dans tout le dépôt, et un test l'impose

commit: fix(phase3): P9F23 — encodage UTF-8 imposé aux sorties de Node, et garde sur la classe entière

## Contexte

CI rouge sur `5f8fc6f` (P9F21) : **les trois jobs Windows** échouent, alors que les quatre autres
passent. Même symptôme que P9F17, sur un test neuf :

    tests\test_phase3_p9f21.py:404
    assert ['<p class="n...e en échec)'] == ['<p class="n...le en �chec)']

Le test lance Node, capture sa sortie avec `subprocess.run(..., text=True)`, et Windows la décode avec
l'encodage local (cp1252) : le « é » de « en échec » devient un caractère de remplacement, l'égalité
tombe, et le produit n'a rien à voir là-dedans.

C'est la **deuxième fois** : P9F17 avait corrigé exactement ce défaut dans `_render_settings_panel`,
en précisant que `text=True` sans encodage explicite est un piège sous Windows. Le correctif ponctuel
n'a pas empêché la récidive : il faut traiter la classe.

## Ce que l'étape doit faire

### 1. Corriger les occurrences, pas seulement celle qui a rougi

Recenser, dans `tests/`, **tous** les `subprocess.run`/`Popen` qui capturent la sortie de `node` (ou
de tout outil produisant de l'UTF-8) sans `encoding="utf-8"`, et les corriger. Un `text=True` nu dans
ce contexte est le défaut ; `encoding="utf-8"` le remplace.

La même revue vaut pour les comparaisons de texte issu de Node dans les tests : elles doivent lire en
UTF-8, pas dans l'encodage de la machine.

### 2. Une garde qui empêche la récidive

Un test de `tests/test_ci_workflows.py` (là où vivent déjà les gardes de dépôt) parcourt les sources
de `tests/` et échoue si un appel à `subprocess.run` ou `Popen` mentionne `node` sans
`encoding="utf-8"` dans la même expression. La détection peut être simple — découpage en appels
parenthésés, comme les autres gardes du fichier — mais elle doit **nommer le fichier et la ligne**
pour qu'on sache quoi corriger.

Ce test échoue aujourd'hui, par construction : il est écrit pour attraper l'occurrence de P9F21 **et**
toutes les suivantes.

### 3. Ce qui n'est pas concerné

Les appels qui ne capturent rien (`check=True` sans `capture_output`), ceux qui lisent des octets
(`text=False`, `.read()` sur `bytes`), et les outils qui produisent de l'ASCII ne demandent rien. La
garde ne doit pas produire de faux positifs au point qu'on la désactive : si un cas légitime résiste,
il se déclare par un commentaire explicite que la garde reconnaît, plutôt que par un contournement.

## Règles

- Fichiers autorisés : `tests/test_phase3_p9f21.py`, `tests/test_setup_flow.py`,
  `tests/test_ci_workflows.py`, tout autre fichier de `tests/` portant l'occurrence,
  `docs/campaigns/phase3/limites-connues.md`.
- Aucune assertion existante ne doit être affaiblie : on change la façon de lire, pas ce qui est
  vérifié.
- Un test par comportement, qui **échoue si la correction est retirée**, mutation citée :
  - le test de P9F21 qui compare le HTML passe, et une réintroduction de `text=True` le fait tomber ;
  - la garde détecte une occurrence fabriquée (fichier temporaire) en nommant fichier et ligne ;
  - la garde ne signale pas un appel qui lit des octets ni un appel sans capture.
- Un seul commit, sujet exactement :
  `fix(phase3): P9F23 — encodage UTF-8 imposé aux sorties de Node, et garde sur la classe entière`.

## Definition of done

- Plus aucun `subprocess` de test ne décode la sortie de Node avec l'encodage local.
- La garde nomme fichier et ligne, et passe sur le dépôt corrigé.
- `.venv/bin/python -m pytest -q` vert sous Linux, plus de tests qu'avant (3 066), 16 skips inchangés.
- Un seul commit, sujet ci-dessus.
- Réponse finale en français : la cause exacte, les occurrences corrigées, ce que la garde empêche, et
  le fait que la preuve finale est **la CI Windows verte sur ce commit**.
