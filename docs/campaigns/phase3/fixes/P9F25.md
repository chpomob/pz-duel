# P9F25 — Le sexe des zombies envoyés suit la tenue, et la tenue doit exister

commit: fix(phase3): P9F25 — sexe des zombies accordé à la tenue, et liste tirée du registre du jeu

## Contexte

Session du 16/11 : « les strip-teaseuses, je suis pas sûr que tous les pops soient bien gérés, y a
peut-être un souci de sexe des z ». Vérifié dans le jeu, et c'est exact — pour trois raisons distinctes.

### 1. Le mod ne dit jamais le sexe

`addZombiesInOutfit` a six paramètres : `(x, y, z, count, outfit, sex)`. Le sixième est un pourcentage
de femelles, lu dans le bytecode de `LuaManager$GlobalObject` :

    if (sex != null) zombie.setFemaleEtc(Rand.Next(100) < sex.intValue());

Le tutoriel du jeu l'utilise : `addZombiesInOutfit(..., "TutorialMom", 100)` et `"TutorialDad", 0`.
Notre `spawnAt` passe `nil` : **`setFemaleEtc` n'est jamais appelé**, le sexe reste celui tiré par
`createRealZombieAlways`. Une tenue féminine atterrit donc sur un homme une fois sur deux.

### 2. Le registre des tenues est séparé par sexe

`media/clothing/clothing.xml` contient deux listes, `m_FemaleOutfits` (170) et `m_MaleOutfits` (239).
Un nom absent de la liste du sexe tiré ne s'applique pas — le zombie retombe sur « No Outfit ». Dans
notre table (`service/settings.py:117-138`), six entrées sont dans une seule liste :

    Inmate            masculin seulement
    PrisonGuard       masculin seulement
    StripperBlack     féminin seulement
    StripperNaked     féminin seulement
    CowboyStripper    masculin seulement
    PoliceStripper    masculin seulement
    FiremanStripper   masculin seulement

Et trois des « strip-teaseuses » de notre table sont en réalité les variantes **masculines** du jeu
(`CowboyStripper`, `PoliceStripper`, `FiremanStripper` figurent dans `m_MaleOutfits`).

### 3. `StripperWhite` n'existe dans aucune des deux listes

Notre entrée « Strip-teaseuse, tenue blanche » ne correspond à aucune tenue du registre : elle est
présente dans `ZombiesZoneDefinition.lua` mais pas dans `clothing.xml`. Choisie, elle ne produit donc
jamais la tenue demandée, quel que soit le sexe. Les noms féminins réels sont `StripperPink`,
`StripperBlack`, `StripperNaked` et `WaiterStripper` ; le masculin générique est `Stripper`.

## Ce que l'étape doit faire

### 1. La liste des tenues vient du registre du jeu, pas d'une table écrite à la main

Au démarrage, lire `media/clothing/clothing.xml` (chemin fourni par `service/paths.py`) et en tirer les
noms réellement disponibles, avec leur compatibilité : `female`, `male`, ou `both`. La table de
`service/settings.py` devient une **sélection** de noms (avec leurs libellés français), mais chaque nom
est validé contre le registre : un nom absent est retiré de l'offre et **signalé** dans `setup`, pas
silencieusement proposé. Si le fichier est illisible, la sélection se réduit à `random` et le lobby le
dit — on ne casse pas le démarrage pour un panel de déguisements.

Le réglage reste `zombie_outfit` ; sa valeur par défaut reste `random`.

### 2. Le sexe suit la tenue, et se règle

Nouveau champ de réglages `zombie_sex` : `auto` (défaut), `female`, `male`, `random`.

**Règle qui prime : une tenue qui n'existe que pour un sexe impose ce sexe, à 100 %.** Choisir une
strip-teaseuse féminine ne doit jamais produire un homme à moitié nu : tous les zombies du pop
naissent du bon sexe, sans exception et sans tirage.

- `auto` : `100` si la tenue n'existe qu'en féminin, `0` si elle n'existe qu'en masculin, `random`
  sinon (les deux sexes, comme le jeu). C'est le défaut.
- `female` / `male` : la valeur imposée, mais **seulement pour une tenue qui existe dans ce sexe**.
  Une combinaison incohérente (`female` + `Inmate`, qui est masculin seul) est **refusée au moment du
  réglage**, avec le nom de l'uniforme en cause : le lobby n'enregistre pas un duo qui produirait des
  zombies sans tenue. Pas de repli silencieux, pas de tirage.
- `random` : `nil`, exactement le comportement d'avant, conservé pour comparer.

Le service écrit le sexe dans chaque commande de pop (`sex` entier ou absent), à côté de `outfit` ;
`service/rules.py` le recopie comme la clé `outfit` aujourd'hui.

### 3. Le mod applique et rapporte

`spawnAt` passe le sixième argument quand la commande le porte (`nil` sinon), et `spawnGroup` renvoie
dans son résultat le sexe effectivement obtenu, lu sur les zombies créés :
`sex = { female = n, male = m }`. Un `sex` demandé et non obtenu n'est pas une erreur — c'est un
constat à journaliser, comme `hold_applied` l'a fait pour la tenue du joueur.

Pas de nouvelle capacité : le mod reste compatible avec une version antérieure du service, qui
n'envoie simplement pas `sex`.

- Aucune tenue n'est ajoutée à l'offre sans exister dans le registre lu.
- Le nom reste recopié tel quel jusqu'au jeu : pas de traduction, pas de normalisation.
- Un test par comportement, qui **échoue si la correction est retirée**, mutation citée :
  - `auto` + tenue féminine seule → commande portant `sex = 100` ;
  - `auto` + tenue des deux sexes → pas de `sex` ;
  - nom absent du registre → retiré de l'offre et signalé, jamais envoyé ;
  - registre illisible → offre réduite à `random`, démarrage intact ;
  - le mod rapporte `sex = {female, male}` d'après les zombies créés.
