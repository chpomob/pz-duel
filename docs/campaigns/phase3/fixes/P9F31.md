# P9F31 — Un binaire Windows à jour après chaque CI verte, et qui dit sa version

commit: feat(phase3): P9F31 — release de test roulante depuis master, et identité du binaire

## Contexte

Question du propriétaire : « est-ce qu'on génère un `.exe` régulièrement, que les testeurs Windows
aient une version à jour ? »

Non. `release.yml` ne construit le binaire que sur un tag `v*`, poussé à la main. Le dernier est
`v0.0.0-phase3-test2`, du **10 novembre** — une trentaine de commits en arrière. Le testeur qui
télécharge la release joue donc une version :

- sans le verrou du départ réparé (P9F26 : `setIgnoreMovement`),
- sans le sexe des zombies (P9F25),
- sans les annonces à l'écran (P9F22), sans les réglages (P9F15), sans le mode arbitre (P9F14),
- sans les lots corrigés (P9F9).

Il ne peut pas non plus savoir **quelle** version il exécute : le binaire ne porte aucune identité.

## Ce que l'étape doit faire

### 1. Une release de test roulante, sur la CI verte de `master`

Dans `tests.yml`, un job `test-build` :

- `needs: [pytest, pytest-windows]` — donc jamais avant que les deux suites passent ;
- `if:` limité à `github.ref == 'refs/heads/master'` **et** `github.event_name == 'push'` : les
  pull requests ne construisent rien ;
- même construction que `release.yml` (même spec PyInstaller, mêmes empreintes, test de fumée) ;
- publication dans une release **au tag fixe `test`**, en pré-release, avec `--clobber` :

      https://github.com/<owner>/<repo>/releases/download/test/pz-duel.exe

  Une URL unique, toujours la dernière version verte. Les notes portent le sha court, le sha complet,
  l'heure de construction et le sujet du commit ; la release est créée au premier passage, éditée
  ensuite (`gh release edit test --notes …`).

Le job reçoit `contents: write` et lui seul ; le reste du workflow garde `contents: read`.

Les releases `v*` restent ce qu'elles sont : des jalons versionnés, publiés à la main.

### 2. Le binaire dit ce qu'il est

- `service/build_info.py` expose `build_id()` : un dict `{id, sha, built_at}` lu dans un fichier
  d'empreinte déposé au moment de la construction (`packaging/_build_stamp.json`, embarqué par
  PyInstaller). Depuis les sources, ou si le fichier manque ou est illisible, il rend
  `{"id": "dev", "sha": null, "built_at": null}` — jamais d'exception, jamais de démarrage cassé.
- `pz-duel.exe --version` affiche cette identité et sort en 0, sans lancer le serveur : un testeur peut
  répondre « je suis sur master-53068e1 » sans ouvrir l'interface.
- `GET /api/state` publie `build`, et le pied du lobby l'affiche discrètement (`master-53068e1`).
  C'est ce qui permet, au téléphone, de savoir ce que le testeur exécute réellement.

### 3. Un garde-fou contre la dérive

Un test de dépôt vérifie que le job `test-build` existe dans `tests.yml`, qu'il dépend des deux suites,
qu'il ne se déclenche que sur `master` en push, et qu'il publie au tag `test` avec `--clobber`. La
prochaine fois qu'on touchera au workflow, l'invariant sera relu.

## Règles

- Fichiers autorisés : `service/build_info.py` (nouveau), `service/main.py`, `service/state.py`,
  `service/engine.py` si l'état y est composé, `packaging/pz-duel.spec`,
  `packaging/pz_duel_entry.py`, `packaging/smoke_test.py`, `.github/workflows/tests.yml`, `ui/app.js`,
  `tests/`, `docs/campaigns/phase3/limites-connues.md`.
- Aucune donnée secrète dans l'empreinte : ni chemin de machine, ni nom d'utilisateur, ni jeton.
- Le binaire depuis les sources ne doit rien changer au comportement actuel : `dev` est la valeur
  neutre.
- Un test par comportement, qui **échoue si la correction est retirée**, mutation citée :
  - `build_id()` lit l'empreinte quand elle existe, rend `dev` sinon, et survit à un fichier illisible ;
  - `--version` sort en 0 et imprime l'identité, sans ouvrir de port ;
  - `/api/state` porte `build` et le lobby l'affiche ;
  - le garde-fou du workflow détecte une modification qui retirerait la condition `master` ou le
    `needs`.
- Un seul commit, sujet exactement :
  `feat(phase3): P9F31 — release de test roulante depuis master, et identité du binaire`.

## Definition of done

- Le job existe et ne peut pas publier avant les deux suites, ni depuis une pull request.
- L'URL `releases/download/test/pz-duel.exe` existe après la première CI verte qui suit la fusion.
- `pz-duel.exe --version` et le pied du lobby donnent la même identité.
- `.venv/bin/python -m pytest -q` vert, plus de tests qu'avant (3 204), 16 skips inchangés.
- Un seul commit, sujet ci-dessus.
- Réponse finale en français : l'URL à donner aux testeurs, ce que le binaire affiche comme version,
  et ce qui reste manuel (les releases versionnées, et le fait que la release roulante n'est pas signée).
