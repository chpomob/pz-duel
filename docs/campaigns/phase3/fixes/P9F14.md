# P9F14 — Mode arbitre : deux invités, personne ne joue sur la machine qui héberge

commit: feat(phase3): P9F14 — mode arbitre : deux invitations, aucun joueur local

## Contexte

Aujourd'hui le PC qui lance PZ Duel **héberge les deux serveurs et joue l'un des deux camps** :
`open_game` ouvre le client local, l'invitation unique désigne la machine de l'hôte, et
`host_password` est traité comme un secret de machine — l'API refuse explicitement de le faire sortir
(« `invite` sort par l'API : jamais `host_password` »).

Demande du propriétaire : « il faudrait séparer le serveur et les joueurs, avoir deux invités, que le
serveur ne soit pas forcément un joueur ».

## Ce que l'étape doit faire

### 1. Un choix au départ, pas un remplacement

Au lancement d'un match, le lobby propose **qui joue** :

- **« Moi et un invité »** — comportement d'aujourd'hui, inchangé, reste le défaut ;
- **« Deux invités »** — mode arbitre : la machine héberge et arbitre, personne n'y joue.

Le choix se porte par le corps de `POST /api/action {"action":"start", …}` (`mode: "host" | "referee"`)
et se lit dans `/api/state` (`mode`). Aucun réglage dans les presets : c'est une décision de session.

### 2. En mode arbitre, deux invitations complètes

- **Deux invitations, A et B**, chacune avec son lien, son code de lanceur et son `.bat` :
  `GET /api/invite/launcher?side=A|B`. En mode hôte, seul B existe, comme aujourd'hui.
- **Les ports de A sont exposés** comme ceux de B : six redirections UPnP (17271 et 17272 UDP,
  17280 TCP pour chaque camp), toujours sur des ports externes ≥ 49152 et toujours avec la description
  « PZ Duel ». Un échec sur A est annoncé séparément de B.
- **`open_game` n'a plus d'objet** : en mode arbitre, l'action répond `refused, reason: no_local_player`
  et le bouton n'existe pas dans l'interface.
- **`host_password` devient l'accès d'un joueur** : il figure dans l'invitation de A, comme le mot de
  passe de B figure dans celle de B. C'est un renversement assumé d'une décision antérieure, écrit
  dans `limites-connues.md` avec la raison : en mode arbitre, ce mot de passe n'est plus un secret de
  machine mais l'accès d'un participant, qui doit pouvoir se connecter depuis chez lui.

### 3. Ce qui ne change pas

- La tenue : les deux mondes restent figés tant que **les deux** joueurs ne sont pas là (P9F10-P9F12),
  quel que soit le mode. En mode arbitre, personne ne peut donc entrer et jouer avant l'autre.
- Deux secrets restent séparés, par camp (code du lanceur, mot de passe serveur).
- Le duel, les règles, les presets, la dérive : inchangés.

## Règles

- Fichiers autorisés : `service/engine.py`, `service/api.py`, `service/upnp.py`, `service/guest_launcher.py`,
  `ui/app.js`, `ui/index.html`, `tests/test_upnp.py`, `tests/test_match.py`, `tests/test_guest_launcher.py`,
  `tests/test_setup_flow.py`, `README.md`, `README.fr.md`, `docs/campaigns/phase3/limites-connues.md`.
- Le mode hôte doit rester **strictement** identique, comportement et tests : c'est le défaut.
- Aucun test ne parle à un vrai routeur ; le faux IGD suffit, et un échec de A ne doit pas casser B.
- Un test par comportement, qui **échoue si la correction est retirée**, mutation citée :
  - `mode: "referee"` produit deux invitations et six redirections demandées ;
  - `open_game` refuse en mode arbitre et n'ouvre rien ;
  - l'invitation de A porte le mot de passe de A, celle de B celui de B ;
  - le mode hôte produit exactement une invitation et trois redirections, comme avant.
- Un seul commit, sujet exactement :
  `feat(phase3): P9F14 — mode arbitre : deux invitations, aucun joueur local`.

## Definition of done

- Deux invitations complètes en mode arbitre, avec ports et `.bat` propres à chaque camp.
- `open_game` refusé proprement, sans effet de bord.
- Le mode hôte inchangé, prouvé par ses tests existants qui ne bougent pas.
- `.venv/bin/python -m pytest -q` vert, plus de tests qu'avant (2 847), 16 skips inchangés.
- Un seul commit, sujet ci-dessus.
- Réponse finale en français : ce que voit l'arbitre, ce que reçoit chaque joueur, ce qui a changé
  dans le contrat de `host_password` et pourquoi, et ce qui reste à vérifier en session réelle (deux
  joueurs distants, aucun client sur la machine hôte).
