# P19F5 — Les cinq constats de la re-revue finale

commit: fix(phase2): P19F5 — Limite par pair, permissions de release, texte du code, origine du lanceur

## Contexte

Re-revue finale (`docs/campaigns/phase2/review-final/final.json`), verdict REJECT : les douze constats
de la première passe sont fermés, mais cinq nouveaux apparaissent, aucun majeur. Les cinq sont réels.

### A1 — Le partage peut être affamé par un seul pair
Le partage écoute sur le LAN (AC37) avec `CONNECTIONS_MAX` places et un délai d'en-tête de 5 s, mais
**sans limite par pair**. Un client qui ouvre 32 connexions lentes depuis une seule machine prend
toutes les places et refuse le vrai invité. Ajoute un plafond par adresse source (budget nommé,
configurable dans `runtime.json`), un test qui ouvre `plafond + 1` connexions depuis la même adresse et
vérifie que la dernière est refusée **et** que le refus est le même 503 JSON, et un test qui vérifie
qu'une autre adresse garde sa place.

### A2 — La release publie avec des droits et des épinglages mous
`release.yml` n'a pas de bloc `permissions:` : le job hérite des droits par défaut du dépôt et peut
écrire partout. Ses actions sont épinglées à des tags mouvants (`@v4`, `@v5`). Déclare
`permissions: contents: write` au niveau du workflow (le strict minimum pour créer la release), et
épingle chaque action à un commit complet. Vérifie que `tests/test_ci_workflows.py` couvre ces deux
règles, sinon ajoute le contrôle : un workflow dont une action n'est pas épinglée à 40 caractères
hexadécimaux doit faire échouer le test.

### A3 — Le texte du code ment sur le mécanisme
`ui/app.js` dit à l'hôte que l'invité « doit voir ce code dans son lanceur ». En réalité le lanceur
**demande** le code. Corrige le texte pour décrire ce qui se passe, et ajoute la seule consigne qui
compte côté invité : **un lanceur qui ne demande pas de code ne doit pas être exécuté**. Le texte du
`.bat` doit dire la même chose, au même endroit que la demande.

### A4 — La route du lanceur accepte une navigation cross-site
`GET /api/invite/launcher` ne vérifie que le `Host`. Un site tiers peut déclencher le téléchargement
par une navigation de haut niveau. Refuse la requête quand l'origine annoncée n'est pas la nôtre :
`Origin` présent et différent → 403 JSON ; `Sec-Fetch-Site` présent et valant `cross-site` → 403 JSON ;
absence d'en-tête (vieux client, `curl`) → accepté, comme aujourd'hui. Un test par cas, dont un qui
vérifie qu'un `curl` nu continue de fonctionner.

### A5 — `_build_invite` hache le mod sous le verrou
Même défaut que A8, corrigé ailleurs : calcule l'empreinte **avant** de prendre `self.lock`, puis
construis la réponse sous verrou avec cette empreinte. Un test qui vérifie que `/api/state` répond
pendant qu'une invitation se construit sur un mod lent (ou une assertion équivalente qui échoue si le
hachage revient sous le verrou).
