# P19F6 — Les quatre constats de la synthèse que P19F5 n'a pas couverts

commit: fix(phase2): P19F6 — Vérification certutil documentée, sortie immédiate, code 64 bits, mod conservé

## Contexte

La re-revue finale a deux artefacts : `final.json` (5 constats) et `review.md`, la **synthèse
authoritative**, qui en compte **9**. P19F5 a traité les cinq du JSON. Les quatre autres restent
ouverts, dont un majeur. Ils sont cités ici dans les termes de `review.md`.

### 1. [MAJEUR] Les étapes invité du README sautent la seule vérification qui tient
`README.md:74-81` (étapes invité 1-3) et `README.md:67-68` (étape hôte 6). L'étape 2 dit
« double-cliquez `pz-duel-join.bat` » juste après avoir obtenu le fichier. Or le contrôle embarqué
tourne **dans le fichier contrôlé** : un `.bat` substitué peut simplement l'omettre. Le seul contrôle
qui tient est extérieur — `certutil -hashfile` avant ouverture, avec comparaison du préfixe au code
lu par l'hôte. Le texte in-app (`service/engine.py`, `LAUNCHER_CODE_TEXT`) décrit déjà cette procédure :
le README doit dire la même chose, pas moins.

Corrige : une étape invité **avant** le double-clic (« demandez le code à l'hôte, lancez
`certutil -hashfile pz-duel-join.bat SHA256`, et n'ouvrez pas le fichier si le résultat ne commence pas
par ce code »), et l'étape hôte 6 qui dit de **lire le code à voix haute, séparément du lien**.
Répercute dans `README.fr.md`.

### 2. [MINEUR] Un jeu qui démarre puis se ferme aussitôt est rapporté comme un succès
`service/guest_launcher.py:216-223`. `[void][Diagnostics.Process]::Start($info)` jette l'objet
processus, `$code = 0` par défaut, et le `finally` supprime `$stage` — donc `previous`, le mod
antérieur de l'invité — alors que le README promet « en cas d'échec, votre mod existant est laissé
tel quel ».

Corrige : après le lancement, **vérifie que le client tourne** (attente bornée de l'apparition du
processus `ProjectZomboid64`, budget nommé). S'il n'apparaît pas, c'est un échec : message explicite,
`previous` restauré, `$stage` conservé. Attention au transfert `UseShellExecute=$true` : si le client
délègue à un processus enfant, la détection doit viser le processus du jeu, pas celui du shell.

### 3. [MINEUR] Le code de vérification fait 48 bits, marge jugée faible
`service/guest_launcher.py:40` : `LAUNCHER_CODE_CHARS = 12` (12 hexadécimaux = 48 bits). Passe à
**16** caractères (64 bits), mets à jour le commentaire de calibrage, la documentation
(`docs/campaigns/phase2/limites-connues.md` et `.fr.md`) et tout endroit qui cite 48 bits ou 12
caractères. La comparaison `certutil` reste un préfixe, elle s'adapte d'elle-même.

### 4. [NIT] Un lancement réussi supprime silencieusement le `duelcore` précédent
`service/guest_launcher.py:285` et `:300-304`. Conserve l'ancien dossier sous un nom explicite
(`duelcore.previous`, ou équivalent) au lieu de le supprimer, et **dis-le** dans la sortie du
lanceur : l'invité doit savoir qu'il peut revenir en arrière.

### 5. Complément du constat 3 (approvisionnement de la release)
`pip install -r packaging/requirements-build.txt` sans `--require-hashes` : une dépendance compromise
produirait un binaire dont le `.sha256` attesterait fidèlement. Ajoute les empreintes exigées
(`--require-hashes` avec versions exactes et `--hash=sha256:…`), et vérifie que le workflow de test
et celui de release utilisent le même fichier. Si c'est impossible sans casser la construction,
arrête-toi et explique pourquoi plutôt que de laisser le trou.
