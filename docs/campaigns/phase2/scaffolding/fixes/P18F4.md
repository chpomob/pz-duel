# P18F4 — Le refus de connexion coupe la réponse sous Windows (WinError 10053)

commit: fix(phase2): P18F4 — Le refus de connexion se termine en FIN, jamais en RST

## Contexte

CI réelle du commit `e8d5401` (run **42313084724**). Deux jobs Windows sur trois sont verts, et il
n'en reste **qu'un seul échec**, sur `pytest-windows (3.13)` :

```
1 failed, 2118 passed, 29 skipped
_______ test_ac40_connections_are_capped _______
E  ConnectionAbortedError: [WinError 10053] An established connection was aborted by the
   software in your host machine
```

Les jobs 3.12 et 3.14 passent le même test : c'est une course, pas une différence systématique. La
cause est visible dans `service/api.py:463-471` :

```python
request.setblocking(False)
request.send(turned_away())
request.shutdown(socket.SHUT_WR)
request.recv(DRAIN_CHUNK)  # fermer sur des octets non lus couperait le refus
```

Le socket est **non bloquant** avant le `recv` : quand la requête du client n'est pas encore arrivée
au moment du `send` (cas fréquent, et variable selon la vitesse de la machine), le `recv` rend
immédiatement `EWOULDBLOCK`, on ferme sur des octets non lus, et Windows envoie un **RST** au lieu
d'un FIN. Le client ne lit jamais son 503 : il reçoit `WinError 10053`.

## Correction attendue

- Le refus doit se terminer proprement sur toutes les plateformes : le client lit le 503 puis un FIN.
  Corrige la vidange, pas le client — un vrai client (navigateur, lanceur) subit le même RST.
- La vidange reste **bornée** : elle ne doit jamais immobiliser le fil d'`accept` au-delà d'un budget
  court et explicite (attente bornée sur la lisibilité, puis vidage jusqu'à la fin du budget ou EOF).
  Le budget vit dans `runtime.json` ou dans une constante nommée avec sa justification écrite.
- Un test qui reproduit le défaut : sous Windows, un client qui reçoit un refus doit lire
  `HTTP/1.0 503` et non lever `ConnectionAbortedError`. Ce test doit échouer sur le code d'avant.
- Les tests existants de plafond de connexions restent inchangés.

## Preuve exigée

- Sous Linux, la suite complète reste verte (2 098 tests, 5 skips).
- **Exécution réelle sous `windows-latest`** : les trois `pytest-windows` doivent passer. Étant donné
  que le défaut est une course, une seule exécution verte ne suffit pas à conclure : l'opérateur
  relancera la CI au moins deux fois, et le test de course doit être conçu pour échouer de façon
  déterministe sur l'ancien code (par exemple en n'envoyant la requête qu'après le début du refus).

## Règles

- Ne modifie que `service/api.py`, `service/runtime.json` et les tests de `tests/test_share.py`
  touchant le plafond de connexions.
- Aucune assertion retirée, aucun test ignoré, aucun délai augmenté sans budget nommé et justifié.
- Un seul commit, sujet : `fix(phase2): P18F4 — Le refus de connexion se termine en FIN, jamais en RST`.
- Réponse finale en français : mécanisme retenu, budget choisi et pourquoi, comment le test échoue
  sur l'ancien code.
